1. Introducción Oficial

¿Qué es FluxDB?

FluxDB es una base de datos distribuida en memoria y un motor ECS (Entity Component System) híbrido de ultra-alta velocidad programado en C++17 nativo. Ha sido diseñado específicamente para resolver los cuellos de botella de sincronización, rendimiento de caché y netcode que sufren las simulaciones masivas y los motores de videojuegos modernos (Unreal Engine 5, Unity DOTS, Flecs y servidores multijugador dedicados).

¿En qué se especializa?

FluxDB no intenta ser una base de datos relacional tradicional (como PostgreSQL) ni un simple almacén clave-valor (como Redis). Se especializa en:

🎮 Netcode de Rollback Determinista
Captura snapshots estructurales con costo Copy-On-Write (COW) y resimula frames pasados instantáneamente.
⚡ Layout Cache-Friendly SIMD
Estructuración contigua por arquetipos en formatos SoA y AoSoA (Array-of-Structs-of-Arrays) de ancho de carril SIMD.
🌐 Espacialidad Nativa Infinta
Índices Octree O(1) combinados con coordenadas de sector de 64 bits (SectorPos) para origin rebasing sin tirones.
🤖 IA Nativa e Hiper-Versionado
Almacenamiento nativo para Blackboards, planos GOAP y Árboles de Comportamiento con versionado fino por tick.

¿Por qué FluxDB?

En el desarrollo de videojuegos y simulaciones en tiempo real, las bases de datos convencionales introducen latencias de milisegundos inaceptables en el game loop. Por otro lado, los motores ECS tradicionales carecen de:

  • Versionado histórico nativo: Imposibilidad de consultar cómo estaba el mundo en el tick $N-10$ sin duplicar toda la memoria.
  • Replicación de red automática: La serialización de deltas suele requerir código manual propenso a errores.
  • Hot-Reload de componentes en vivo: Modificar una estructura en tiempo de ejecución solía requerir reiniciar la simulación.

FluxDB integra todas estas necesidades directamente en la capa de almacenamiento de memoria contigua.

¿Qué hace exactamente?

FluxDB administra la memoria de tu aplicación organizando las entidades en Arquetipos (combinaciones únicas de componentes). Cada componente vive en un array contiguo de páginas. Cuando se realiza un cambio:

  1. El TickRing sella la versión exacta de la escritura.
  2. El Unified Delta Engine calcula automáticamente la diferencia bit a bit y empaqueta la delta comprimida en RLE/Cuantizado.
  3. Si ocurre desincronización de red, el sistema de Causal Divergence Tracing rastrea exactamente qué sistema y qué tick causó la diferencia en 8 microsegundos.

2. Arquitectura y Teoría Completa

Arquitectura de Memoria: SoA, AoSoA y Clasificación Hot/Warm/Cold

FluxDB clasifica los componentes en tres niveles de acceso según su frecuencia de uso en el ciclo de frame:

  • HOT: Componentes modificados cada frame (p. ej. Position, Velocity).
  • WARM: Componentes consultados con frecuencia media (p. ej. Health, Target).
  • COLD: Componentes raras veces leídos (p. ej. QuestFlags, Inventory).

En iteraciones AoSoA (Array-of-Structs-of-Arrays), las entidades se agrupan en carriles de ancho SIMD (8 floats contiguos). Una consulta que toca solo componentes HOT nunca arrastra las líneas de caché L1/L2 de los componentes COLD.

Snapshots Copy-On-Write (COW) & Netcode de Rollback

Cuando se captura un snapshot del mundo mediante WorldSnapshot::capture(world), FluxDB NO realiza una copia profunda (deep-copy) de los datos de los componentes. En su lugar:

💡 Mecanismo Copy-On-Write (COW)
El snapshot comparte las páginas de memoria de los chunks con el estado activo mediante std::shared_ptr. Si una página no se modifica durante el rollback, el costo de captura es $O(\text{páginas})$ en lugar de $O(\text{bytes})$. Si una entidad escribe en una página compartida, esta se clona in-place transparentemente.

Versionado Temporal y TickRings Coarse-to-Fine

FluxDB mantiene un registro exacto del tick del último write por componente y entidad. El sistema de escaneo for_each_changed_entity opera en dos niveles:

  1. Coarse Granular (O(1)): Un TickRing a nivel de chunk comprueba si alguno de los elementos del rango tuvo modificaciones posteriores a since_tick. Si no hubo cambios, el chunk completo (512 filas) se ignora instantáneamente.
  2. Fine Granular: Dentro de chunks sucios, se escanea únicamente el array de ticks del componente.

Unified Delta Engine & Codecs de Compresión

El DeltaSet analiza las firmas de versión de las entidades y empaqueta solo los campos modificados. Para reducir el consumo de red, utiliza codificadores especializados:

  • RleCodec: Compresión Run-Length para bloques de datos repetitivos (logrando más del 98% de reducción en estructuras de estado).
  • QUANTIZED_FLOAT: Cuantización de coordenadas flotantes 3D a enteros escalados de 16 bits para un ancho de banda óptimo.

Grafos de Relaciones Nativas (#6)

Las relaciones en FluxDB son aristas directas $(src, kind, dst)$ almacenadas en listas de adyacencia co-localizadas en memoria. Permiten definir jerarquías complejas como torretas montadas en naves (CHILD_OF) o fijación de objetivos (TARGET_OF) con payloads de hasta 8 bytes.

Octree 3D O(1) & Origin Rebasing Infinito (SectorPos)

Para evitar los problemas de imprecisión de punto flotante en mundos masivos, FluxDB implementa coordenadas de sector de 64 bits (SectorPos). Las entidades se insertan en un SpatialSectorGrid que mantiene subdivisión espacial por octree dentro de cada sector del universo.

IA Nativa: Blackboard, GOAP y Behavior Trees

Los componentes de Inteligencia Artificial están integrados en el layout de almacenamiento:

  • Blackboard: Almacena variables de estado clave-valor optimizadas para consultas masivas.
  • GOAP (Goal-Oriented Action Planning): Calculador A* determinista capaz de generar más de 27,000 planes de acción por milisegundo.
  • Behavior Tree: Evaluador contiguo de nodos Selector, Sequence, Condition y Action.

Trazado de Divergencia Causal & Profiling de Caché

En caso de desincronización entre cliente y servidor, CausalDivergenceTracer compara los hashes de estado tick a tick. Al detectar una diferencia, recorre en reversa la cadena causal de escrituras identificando el componente, la entidad y el sistema exacto responsable en menos de 10 microsegundos.

3. Ejemplos de Código y API Reference

1. Setup Básico del World y ComponentStore

Registro de componentes con asignación explícita de tiers (Hot/Warm/Cold) e inicialización del World.

cpp / setup_world.cpp 
#include "core/headers/ecs.h"

using namespace fluxdb::ecs;

struct Position { float x, y, z; };
struct Velocity { float x, y, z; };
struct Health   { int hp; };

int main() {
    // 1. Registro de tipos de componentes con Tiers de memoria
    auto store = std::make_shared<ComponentStore>();
    ComponentID pos_id = store->register_component("Position", sizeof(Position), ComponentTier::HOT);
    ComponentID vel_id = store->register_component("Velocity", sizeof(Velocity), ComponentTier::HOT);
    ComponentID hp_id  = store->register_component("Health",   sizeof(Health),   ComponentTier::WARM);

    // 2. Inicialización del World con administrador de historial de ticks
    World world(store, std::make_shared<HistoryManager>(200));
    
    return 0;
}

2. Spawning de Entidades y Consultas Compiladas

Población masiva e iteración optimizada sobre arquetipos contiguos.

cpp / ecs_queries.cpp 
// Spawning de 100,000 entidades
Position p{0, 0, 0};
Velocity v{1.5f, 0.0f, 0.0f};
Health h{100};

for (int i = 0; i < 100000; ++i) {
    Entity e = world.spawn();
    p.x = static_cast<float>(i);
    world.add_component(e, pos_id, &p);
    world.add_component(e, vel_id, &v);
    if (i % 2 == 0) world.add_component(e, hp_id, &h);
}

// Iteración ultrarrápida sobre arquetipos (Consultas Compiladas)
world.advance_tick();
for (const auto& [sig, arch] : world.get_archetypes()) {
    size_t count = arch->get_entity_count();
    Position* pos_array = reinterpret_cast<Position*>(arch->get_component_array(pos_id));
    Velocity* vel_array = reinterpret_cast<Velocity*>(arch->get_component_array(vel_id));

    if (pos_array && vel_array) {
        for (size_t i = 0; i < count; ++i) {
            pos_array[i].x += vel_array[i].x * 0.016f;
        }
    }
}

3. Jerarquías de Entidades y Grafos de Relación

Modelado de torretas montadas en naves nodriza usando la relación nativa CHILD_OF.

cpp / relations_demo.cpp 
#include "core/headers/relations.h"

using namespace fluxdb::relations;

RelationGraph relations;
const RelationKind CHILD_OF_KIND = 1;

Entity ship = world.spawn();
Entity turret = world.spawn();

// Establecer relación: Turret es hija de Ship
relations.add_relation(turret, CHILD_OF_KIND, ship);

// Actualizar posición de la torreta en función de la nave padre
relations.for_each_incoming(ship, CHILD_OF_KIND, [&](Entity child_turret, const RelationPayload& payload) {
    Position tur_pos{p.x, p.y + 1.0f, p.z};
    world.add_component(child_turret, pos_id, &tur_pos);
});

5. Rollback Netcode y Captura de Snapshots (COW)

Captura de estado instantáneo, avance de ticks y resimulación en caso de predicción fallida de red.

cpp / rollback_netcode.cpp 
#include "core/headers/rollback.h"

using namespace fluxdb::rollback;

WorldSnapshot snap;

// Captura de Snapshot con costo O(páginas) gracias a Copy-On-Write
snap.capture(world);
uint64_t saved_tick = snap.tick();

// Avance de 10 ticks simulados
for (int t = 0; t < 10; ++t) {
    world.advance_tick();
}

// Se recibe paquete de servidor: ¡Predicción incorrecta! -> Restauración instantánea
if (snap.captured()) {
    snap.restore(world); // El mundo vuelve exactamente al saved_tick
}

GoapPlanner planner;

7. Modding, Schema Evolution y Hot-Reload en Caliente

Modificación del stride de un componente en tiempo de ejecución sin detener el servidor ni reiniciar el juego.

cpp / schema_hot_reload.cpp 
// Reestructuración de memoria in-place: expandir componente Stats de 8B a 12B
Archetype::FieldMap field_map[2] = {
    {0, 0, 4}, // campo atk (offset 0 -> offset 0, len 4)
    {4, 4, 4}  // campo def (offset 4 -> offset 4, len 4)
};

// Migrar 100,000 entidades activas en < 0.4 milisegundos
size_t migrated_rows = world.hot_reload_component(stats_id, 12, field_map, 2, 0);
std::cout << "Filas migradas exitosamente en caliente: " << migrated_rows << std::endl;
